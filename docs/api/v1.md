# Public API v1

**Status:** Stateless planning with evidence-backed Checklists (issues #37, #40, and #55)

The Django Ninja API is mounted at `/v1/`. It assumes a same-origin or reverse-proxied
Next.js deployment. Cross-origin hosting requires a separate CORS and deployment decision.
Neither endpoint uses cookie authentication or mutates application state.

## Active Service navigation

`GET /v1/services` returns active Services ordered by stable semantic ID:

```json
{"services":[{"id":"stable.service.id","title":{"ar":"خدمة","en":"Service"}}]}
```

A Service is active only when its editorial `is_active` flag is true. Dates, predicates,
and the existence of a published version never imply activation. Inactive Services remain
in the planning snapshot so planning can distinguish them from unknown IDs, but they are
not listed or evaluated. Navigation exposes no candidates, questions, rules, versions, or
authoring metadata.

## Stateless planning

`POST /v1/planning` accepts exactly:

```json
{
  "service_id": "stable.service.id",
  "facts": {"fact_key": "transport value"},
  "locale": "ar",
  "evaluation_context": {"evaluation_date": "2026-09-01"}
}
```

`service_id` is nonblank and at most 128 characters. Locale is exactly `ar` or `en`.
The evaluation date is a required, canonical, zero-padded calendar `YYYY-MM-DD`; timestamps
and alternate forms are rejected. Fact transport values may only be JSON booleans,
integers, strings, or null. Arrays, objects, and floats are rejected without coercion.
Canonical date strings are decoded only for Facts whose published definition has date kind.
Null is retained and reported as `invalid_fact_value`, not treated as omission. Unknown
fields in every request object are forbidden.

The `facts` object accepts at most **128 Facts**. Each Fact key is at most **128
characters**, and each string transport value is at most **2,048 characters**. Lengths
count Unicode code points in the decoded JSON strings, not UTF-8 bytes, JSON escape
characters, or user-perceived grapheme clusters. These transport limits add no minimum
length or key syntax restriction; Fact definitions still determine domain validity.
Exceeding any limit returns the existing sanitized HTTP 422 `invalid` response with
`invalid_request` diagnostics. These schema limits are separate from the body-byte limit.

`POST /v1/planning` accepts bodies of at most **512 KiB (524,288 bytes)**, measured
before JSON decoding. Exactly 512 KiB is allowed by the size check but must still satisfy
JSON and schema validation. Larger bodies return HTTP 413 with the fixed response
`{"type":"invalid","diagnostics":[{"code":"body_too_large","path":["body"]}]}`.
The application rejects a declared oversized `Content-Length` early and independently
bounds actual bytes available from the request stream (or checks an already cached body).
This planning-only limit does not change Admin uploads or other endpoints. Trusted ingress
must enforce the same byte limit; application checks cannot prevent earlier server/ASGI
buffering. Existing malformed-body HTTP 400 and schema-validation HTTP 422 responses
remain unchanged for bodies within the limit.

All semantic outcomes use HTTP 200 and one stable discriminator:

- `next_question`: `{"type":"next_question","service_id":"...","question":{"id":"...","text":"...","answers":[{"key":"...","kind":"boolean","enum_options":[],"minimum":null}]}}`
- `inconclusive`: `{"type":"inconclusive","reason":"unknown_service","message":"..."}`
- `invalid`: `{"type":"invalid","diagnostics":[{"code":"invalid_fact_value","path":["facts","key"]}]}`
- `plan`: `{"type":"plan","service_id":"...","procedure_id":"...","procedure_version_id":"...","title":"...","checklist_items":[{"id":"...","text":"...","classification":"official_requirement","classification_label":"Official Requirement","quantity":1,"original_quantity":1,"copy_quantity":0,"document_type_id":"...","scope":"procedure","sources":[{"id":"...","authority_id":"...","title":"...","locator":"...","classification":"official","retrieved_on":"2026-08-01"}],"freshness":{"state":"current","verified_on":"2026-08-01","reverify_on":null}}]}`

Reason and diagnostic codes are stable machine-readable contract values. Messages and
question/title text use the requested locale. Case preparation validates source Facts, performs
pinned deterministic derivations, and checks Service contradictions before any Procedure
candidate is evaluated. A resolved, applicable published Procedure Version produces a plan
with its permitted Checklist Items.
A TRUE contradiction returns one sorted, deduplicated
`{"code":"contradictory_facts","path":["facts","source_key"]}` diagnostic per influential,
submitted source Fact. Dominated FALSE or UNKNOWN branches and omitted source Facts are not
reported as correction targets. FALSE and UNKNOWN contradictions do not reject and UNKNOWN
contradiction branches never create Questions. Diagnostics expose no contradiction ID, raw
value, or evaluator trace. Procedure-Version applicability and Checklist Item assembly run only
after selection and version resolution. Unknown version applicability, consequential Checklist
applicability, or inconclusive trust for a dependent Official Requirement returns a stable local
inconclusive reason rather than inventing an answer.

Malformed JSON or a non-object body returns a sanitized HTTP 400; unknown fields, locale,
date, transport values, and Fact count/length limit violations return HTTP 422. Both use
the same `invalid` discriminator and diagnostic code/path shape. Invalid stored knowledge returns HTTP 500 with only
`knowledge_snapshot_invalid`. Database
unavailability returns HTTP 503 with `knowledge_unavailable`. Unexpected planning errors
return a fixed HTTP 500 `invalid` result containing only
`{"code":"internal_error","path":[]}`. This response is identical when Django debug mode is
on or off; traceback, exception, and local-variable rendering is never delegated to Django
Ninja at the planning boundary.

HTTP 422 schema-validation responses contain at most **20 diagnostics**, retaining the
first 20 in the existing validation order. Responses with 20 or fewer diagnostics are
unchanged; additional diagnostics are omitted without a truncation flag or total count.
Diagnostics retain only sanitized codes and paths, never validation input, context, or
exception messages. This cap does not apply to HTTP 200 domain diagnostics or plan content.

## Plan guidance

Plan responses include deterministic `steps` and `warnings` arrays alongside `checklist_items`. A Step contains exactly `id`, localized `text`, `phase`, compact `sources`, and `freshness`. A Warning contains exactly `id`, localized `text`, `severity`, `kind`, `role`, compact `sources`, and `freshness`; product warnings have an empty source array. Steps are ordered by authored phase position and Warnings by authored display position, with semantic IDs as stable tie breakers.

The response never exposes applicability rules, Basis references, order numbers, Evidence Link IDs, passages, locations, contexts or support status, trust traces, Facts, publisher identity, or editorial rationale.

## Privacy and determinism

The application loads one PostgreSQL repeatable-read, read-only snapshot before calling pure
planning. The public `POST /v1/planning` path scopes that snapshot to the requested Service and
its transitive blocking Procedure-dependency graph; the complete Fact registry remains
available for validation and derivation. No request, Ninja schema, model, queryset, or lazy
relation crosses the boundary. Planning performs no ORM reads and is deterministic for
identical input and snapshot. Once a published Procedure Version is resolved and factually
applicable, the plan contains only applicable current Checklist Items with compact Source and
freshness metadata.

The scoped loader also executes the existing global request-time catalog integrity checks as
validation-only reads. This intentionally retains fail-closed behavior for malformed unrelated
rules, contradictions, evidence, routing, unsupported derived definitions, and visible workflow
history owner resolution; those checks are not materialized as unrelated planning DTOs. Full
snapshot loaders remain available to publication and callers that
need the complete catalog. Historical discrepancy and
semantic-preserving re-verification events are limited to owners in the requested graph while
retaining all events needed to reconstruct the requested evaluation date.
Candidate, stale, disputed, unknown, future-retrieved, or otherwise unsupported material is
not asserted. Evidence passages, locations, applicability context, support flags, and other
editorial Evidence Link fields remain private.

Anonymous Case Facts are not written to models, sessions, cookies, caches, request metadata,
or logs. Responses expose neither submitted/raw Facts nor rule ASTs, predicates, evaluation
traces, Evidence Links, publisher identities, discrepancies, or rationale.

The only permitted planning observability representation is the explicit coarse allow-list:
HTTP method, the fixed `/v1/planning` route, HTTP status code, and a coarse error code. It
excludes service-specific Facts and values, Fact keys, request bodies, request/planning DTOs,
prepared Facts, evaluation and selection traces, predicates, exception messages, exception
objects, tracebacks, and stack data. Matching application and Django log records are rewritten
to that representation before configured output. No planning analytics or metrics are
currently emitted. Any future logs, analytics, metrics, APM, or error-reporting integration
must use the same explicit allow-list and must not receive richer planning objects.

## Service Point routing

Every successful `plan` contains a required `routing` object:

```json
{"status":"resolved|partially_resolved|unresolved","destinations":[{"service_point_id":"…","service_point_version_id":"…","association_id":"…","name":"localized text","address":"localized text","availability":"available|unknown","effective_from":"YYYY-MM-DD|null","effective_to":"YYYY-MM-DD|null","sources":[]}],"verification_sources":[]}
```

Destinations are association-distinct and ordered by stable point ID, material-version ID,
and association ID. `resolved` means all locally applicable routing could be evaluated;
`partially_resolved` means at least one trusted destination was found while another route
remains uncertain; `unresolved` means no trusted destination can currently be returned.
Availability `unknown` is a destination attribute, not an unresolved jurisdiction result.

The API localizes `name` and `address` to the requested locale and exposes only compact
Sources. When a researched route is locally unresolved, `verification_sources` provides
preserved supporting provenance as a path for manual verification without asserting that
its routing content is current. It never exposes unresolved association IDs, missing Fact keys, submitted Facts,
predicates, evaluation traces, Evidence Link passages/context/support state, evidence IDs,
or editorial trust rationale. Bardi does not calculate distance or infer a nearest, best,
ranked, regional, or nationwide office. Researched examples establish only their stated
jurisdictions and do not imply national coverage.
